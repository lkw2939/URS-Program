# URS AI REPORT SYSTEM
## 최초 개발 목적·전체 기능·업무 흐름·품질 기준 통합 정의서

**문서 목적:** 처음부터 요구했던 프로그램의 모든 기능과 개발 방향을 명확히 고정하고, 기존 프로그램을 개발할 때 기능 누락·중복 개발·불필요한 연구·임의적인 방향 변경을 방지한다.

---

# Ⅰ. 프로그램의 근본적인 목적

## 1. 어떤 프로그램인가?

URS AI REPORT SYSTEM은 우도산기 직원이 해외 고객으로부터 받은 URS(User Requirement Specification, 사용자 요구사항 명세서)를 신속하고 정확하게 이해하고 검토하기 위한 사내 업무 프로그램이다.

고객이 제공한 영어·인도네시아어 URS PDF를 업로드하면, 프로그램이 ChatGPT/OpenAI를 활용하여 다음 작업을 자동으로 수행한다.

1. 원본 PDF의 전체 내용과 시각자료 보존
2. 원문의 한국어 자동 번역
3. 원문과 번역문의 독립적인 기술적 의미 검증
4. 발견된 번역 오류 자동 수정 및 재검증
5. 설비·공정·성능·기술 요구사항 분석
6. URS 내부의 사양 불일치 및 모순 탐지
7. 고객에게 확인해야 할 기술 질문 작성
8. 전문 한국어 URS 번역본 및 기술 분석 보고서 생성
9. 직원의 원문 대조·수정·AI 대화형 검토
10. 수정 내용 재검증 및 최종 승인

**최종 목표는 정확하고 신뢰할 수 있는 기술 문서를 만들고, 직원이 해외 고객의 요구사항을 이해하여 설비 검토와 영업 협의에 활용하도록 지원하는 것이다.**

## 2. 프로그램이 아닌 것

다음은 프로젝트의 목적이 아니다.

- 새로운 번역 AI 모델을 직접 개발하는 것
- ChatGPT가 이미 제공하는 언어 이해 능력을 별도로 연구하는 것
- 독자적인 범용 PDF 인식 엔진을 개발하는 것
- 기존 PDF 라이브러리로 해결 가능한 기능을 처음부터 다시 만드는 것
- 검증 체크리스트만을 위한 별도의 거대한 관리 시스템을 만드는 것
- 새로운 프로그램을 계속 만들어 기존 프로그램을 대체하는 것

**개발해야 할 것은 하나의 사내 업무 프로그램이지, 별도의 AI 연구 플랫폼이 아니다.**

# Ⅱ. 사용자가 실제로 경험해야 하는 업무 흐름

프로그램을 사용하는 직원의 입장에서 전체 흐름은 다음과 같다.

**직원 로그인**

↓

**외국어 URS PDF 업로드**

↓

**PDF 원본 보존 및 전체 내용 확인**

↓

**ChatGPT/OpenAI 한국어 번역**

↓

**독립적인 원문·번역 의미 검증**

↓

**오류 자동 수정 및 재검증**

↓

**설비·공정·요구사양 기술 분석**

↓

**사양 충돌 탐지 및 고객 기술질의 생성**

↓

**한국어 번역본과 기술 보고서 작성**

↓

**원문·번역 병렬 비교 및 직원 검토**

↓

**AI 대화 수정 및 수정 부분 재검증**

↓

**검증 완료·직원 승인**

↓

**Word/PDF 다운로드**

이 모든 작업은 기존 URS AI REPORT SYSTEM 안에서 수행되어야 한다.

단계 사이에 불필요한 프로그램 전환이나 별도의 번역 모델 실행이 필요해서는 안 된다.

# Ⅲ. 첫 번째 기능 — 원본 PDF 업로드 및 보존

## 1. PDF 파일 업로드

직원이 해외 고객의 URS PDF를 업로드하면 프로그램이 해당 문서를 작업 대상으로 등록한다.

원본 파일은 변형 없이 보관하여 나중에 언제든 다시 확인할 수 있어야 한다.

원본 자료를 분석하거나 번역하는 과정에서 원본 파일 자체를 덮어쓰거나 손상시켜서는 안 된다.

## 2. PDF에서 보존해야 할 정보

원본 PDF에는 단순 문장 외에도 여러 기술 정보가 포함된다.

**텍스트**
- 본문, 제목, 소제목
- URS 요구사항 번호
- 주석, 각주, 표 내부 문장
- 안전·성능·품질 조건
- 기술 용어 및 제품 코드

**표**
- 행과 열
- 각 셀의 내용
- 병합 셀
- 제품별 치수·속도·수량
- 표 제목과 단위
- 셀과 제품의 연결 관계

**시각자료**
- 설비 사진
- 공정 흐름도
- 설비 레이아웃
- 기계 도면
- 그래프와 다이어그램
- 그림 내부의 글자와 설명

**원본 출처**
- 페이지 번호
- 문단 및 줄 위치
- 요구사항 번호
- 표의 행과 열
- 원본 문장에서 해당 내용이 나타나는 위치

이러한 정보를 보존하는 이유는 직원이 번역 결과와 원본을 정확하게 비교할 수 있도록 하기 위해서이다.

## 3. ChatGPT와 기존 PDF 처리 코드의 관계

ChatGPT/OpenAI는 PDF의 텍스트와 시각적 맥락을 이해하는 데 활용한다.

기존 프로그램의 PDF 처리 기능은 원본 파일 보존, 표 구조, 위치 연결, 수치 대조, 시각자료 재사용 등 이미 구현한 기능을 계속 수행한다.

**ChatGPT의 PDF 직접 입력 기능은 기존 PDF 추출 기능을 삭제하거나 대체하라는 의미가 아니다.**

두 기능을 조합해 정확하고 효율적으로 처리하는 것이 목적이다.

새로운 자체 PDF 인식 기술 연구는 원래 프로그램의 필수 목표가 아니다.

# Ⅳ. 두 번째 기능 — ChatGPT 자동 한국어 번역

## 1. 번역 대상

초기 프로그램이 지원해야 할 주요 외국어는 다음과 같다.

- 영어 → 한국어
- 인도네시아어 → 한국어

이후 다른 언어를 추가할 수 있는 확장성은 고려하되, 처음부터 불필요한 다국어 시스템을 크게 개발할 필요는 없다.

## 2. 번역에서 가장 중요한 기준

일반 번역에서는 문장이 자연스럽기만 해도 좋은 평가를 받을 수 있다.

그러나 URS는 설비 설계와 제작에 영향을 주는 기술 문서이므로 **기술적 의미의 정확성이 가장 우선**이다.

예를 들어 다음 원문을 보자.

"The conveyor shall not operate when the safety guard is open."

정확한 의미는 다음과 같다.

"안전 가드가 열려 있을 때 컨베이어는 작동해서는 안 된다."

만약 부정문이 누락되면 안전 요구사항이 완전히 반대로 바뀐다.

따라서 번역 과정에서는 다음 내용을 철저하게 보존해야 한다.

| 구분 | 번역 요구사항 |
|---|---|
| 부정문 | 작동 금지, 사용 금지 등의 의미 유지 |
| 조건문 | 특정 조건에서만 작동하는 요구 유지 |
| 의무 표현 | Shall, Must, Should 등의 요구 수준 구분 |
| 생산속도 | 원문 수치와 단위 정확히 보존 |
| 제품 치수 | 길이·너비·높이·두께 관계 유지 |
| 작동 순서 | 공정 순서와 조건 유지 |
| 설비 명칭 | 문서 전체에서 용어 일관성 확보 |
| 제품 코드 | 원본 문자열 그대로 유지 |
| 고객 요구사항 | 원문에 없는 조건 임의 추가 금지 |

## 3. 전체 문서 번역

프로그램은 일부 문장이나 주요 내용만 번역해서는 안 된다.

**원본 PDF 전체가 번역 대상**이다.

문장뿐 아니라 표 안의 설명, 제목, 주석 및 도면 내부의 번역 대상 문자도 포함해야 한다.

문서가 길어 여러 번에 나누어 처리하더라도 모든 원문 항목이 최종 번역본에 포함되어야 한다.

또 각 번역문이 원본의 어느 부분에 해당하는지 추적할 수 있어야 한다.

## 4. 원본 서식 보존

번역 결과물은 원본 PDF의 구성을 최대한 유지해야 한다.

예를 들어 원본 표가 제품 6종의 크기와 생산속도를 보여준다면, 한국어 번역본에서도 같은 제품과 같은 값이 같은 표 구조 안에 있어야 한다.

원본 그림은 재사용하고, 필요한 경우 그림 안의 외국어 설명만 한국어로 처리한다.

원본의 설비 구성이나 연결 관계를 임의로 변경해서는 안 된다.

# Ⅴ. 세 번째 기능 — 번역 후 독립적인 기술 의미 검증

## 1. 독립 검증의 목적

ChatGPT가 번역했다고 곧바로 정확한 번역으로 확정하지 않는다.

**최초 번역과 구분된 별도의 검증 과정**을 실행해야 한다.

검증 AI는 원문과 한국어 번역문을 비교하면서 실제 기술적 의미가 동일한지 판단한다.

여기서 핵심은 단순히 단어나 숫자가 같은지를 확인하는 것이 아니다.

**원문을 읽은 엔지니어와 번역문을 읽은 엔지니어가 동일한 설비 요구사항을 이해하는지를 확인하는 것**이다.

## 2. 검증해야 할 사항

첫째, 원문의 문장 전체 의미를 확인한다.

둘째, 원문의 요구사항이 누락되었는지 확인한다.

셋째, AI가 원문에 없는 사항을 임의로 추가했는지 확인한다.

넷째, 부정문과 조건문의 의미가 뒤바뀌었는지 확인한다.

다섯째, 의무 표현과 권고 표현이 구분되었는지 확인한다.

여섯째, 설비의 작동 순서와 기술적 관계가 유지되었는지 확인한다.

일곱째, 수치와 단위, 치수, 생산속도 및 제품별 데이터가 정확한지 확인한다.

여덟째, 한국어 문장이 문법적으로 정확하고 자연스러운지 확인한다.

아홉째, 기술 용어와 장비 명칭이 적절한지 확인한다.

열째, 표·그림·원문 자료가 최종 번역 결과에 적절히 반영되었는지 확인한다.

## 3. 검증 결과의 형태

단순히 PASS 또는 FAIL만 출력해서는 안 된다.

오류가 있다면 다음 정보를 연결해야 한다.

| 항목 | 예시 |
|---|---|
| 원본 위치 | 5페이지 RQ-04 |
| 원문 | Minimum speed 120 packs/min |
| 번역문 | 최소 생산속도 102팩/분 |
| 오류 유형 | 수치 불일치 |
| 오류 근거 | 120이 102로 변경됨 |
| 수정 대상 | 해당 번역 문장 |
| 검증 상태 | FAIL |

직원은 이 기록을 보고 오류가 무엇이고 왜 문제인지 이해할 수 있어야 한다.

## 4. 독립 검증의 의미

최초 번역을 만든 AI가 스스로 "정확하다"고 말하는 것은 충분한 검증 근거가 아니다.

원문과 번역을 별도의 검증 요청으로 다시 비교하고, 기존 프로그램의 숫자·단위·제품 코드 검사로 확인 가능한 사항은 추가 검증해야 한다.

동일한 OpenAI 모델을 번역과 독립 검증에 각각 사용할 수 있으나, 별도 요청이라고 해서 모든 오류의 발견이 보장되는 것은 아니다.

불확실한 사항은 사람 검토 대상으로 남긴다.

# Ⅵ. 네 번째 기능 — AI 오류 자동 수정과 재검증

## 1. 단순 검증 프로그램이 아니다

오류를 발견하고 목록만 작성하는 것이 목적이 아니다.

**오류 발견 이후 AI가 직접 해당 오류를 수정하도록 하는 기능**이 핵심이다.

## 2. 자동 수정 흐름

최초 번역이 생성된다.

검증 AI가 원문과 비교한다.

오류가 발견되면 오류 내용과 원문 근거를 기록한다.

수정 AI가 문제 있는 번역을 수정한다.

수정한 문장을 다시 독립적으로 검증한다.

오류가 해결되지 않았다면 다시 수정한다.

모든 필수 검증이 통과하면 다음 단계로 진행한다.

## 3. 수정 범위의 관리

오류가 있는 문장만 수정할 수 있다면 다른 정상 문장을 불필요하게 재작성하지 않는 것이 좋다.

수정된 내용이 다른 요구사항과 연결되어 있다면 관련 부분도 다시 검증해야 한다.

예를 들어 제품 코드를 수정했다면 같은 제품을 참조하는 표와 기술 분석 내용에 영향을 주는지 확인해야 한다.

## 4. 자동 수정이 실패한다면?

AI가 반복적으로 오류를 해결하지 못하거나 원문 자체가 불명확하다면 자동으로 PASS 처리해서는 안 된다.

이러한 사항은 **사람 검토 필요** 상태로 남겨야 한다.

재시도 횟수와 API 사용 비용에는 제한을 두어 무한 반복을 방지한다.

## 5. 오류 수정 이력

프로그램은 다음 기록을 보관해야 한다.

- 최초 번역문
- 발견된 오류
- 오류의 원본 근거
- 수정된 번역문
- 수정 후 검증 결과
- 해결되지 않은 문제
- 직원이 수정한 내용과 검토 결과

이 기록은 직원이 문서의 신뢰성을 판단하는 데 활용된다.

# Ⅶ. 다섯 번째 기능 — 설비 및 공정의 기술적 분석

## 1. 단순 번역과 기술 분석의 차이

고객이 URS에 "The machine shall be equipped with a servo motor"라고 작성했다면 번역 기능은 다음과 같이 처리한다.

"기계에는 서보모터가 장착되어야 한다."

그다음 기술 분석 기능에서는 서보모터가 무엇인지, 어떤 역할을 수행하는지, 자동화 장비에서 왜 사용되는지 설명할 수 있어야 한다.

**고객 원문 요구사항과 AI가 추가한 기술 해설은 반드시 구분한다.**

## 2. 설비별 기술 설명

프로그램은 URS에서 언급되는 주요 설비와 공정을 파악해 직원이 이해하기 쉬운 한국어로 설명해야 한다.

예를 들어 다음 항목이 해당된다.

- 컨베이어와 제품 이송
- Sorting 및 제품 방향 정렬
- Counting 및 수량 확인
- Stacking 및 적층
- Cartoning 및 제품 박스 투입
- Wrapping 및 Shrink Packaging
- Weight Checking
- Case Packing
- Rejector 및 불량품 배출
- 서보모터, 공압 장치, 센서, PLC 등의 주요 제어 요소

위 내용은 예시이며, 실제 분석 대상은 **업로드된 고객 URS에 존재하는 설비와 요구사항**이다.

## 3. 공정 순서 분석

고객 URS에서 제품이 어떤 공정을 거치는지 파악한다.

예를 들어 다음과 같은 공정이 있을 수 있다.

Sachet Sorting → Counting & Stacking → Innerbox Cartoning → Weight Checking → Wrapping → Shrinking → Showcase Cartoning → Master Box Packing

프로그램은 공정 순서를 설명하고, 각 공정이 앞뒤 설비와 어떤 관계가 있는지 분석해야 한다.

## 4. 생산능력 분석

제품 공급 속도, 박스 처리 속도, 포장 단위 등을 단순 나열하는 데 그쳐서는 안 된다.

예를 들어 고객이 Sorting 600 sachets/min과 Wrapping 60 packs/min을 요구한다고 해도, 각각 처리하는 단위가 다르므로 수치만 보고 두 공정이 충돌한다고 단정하면 안 된다.

한 팩 또는 박스에 몇 개의 제품이 들어가는지 분석하고, 필요한 정보가 없다면 확인 필요 사항으로 표시해야 한다.

## 5. 기술적 위험 및 확인사항 분석

URS에 근거가 있는 범위에서 기술적 위험과 설계 검토사항을 설명할 수 있어야 한다.

예를 들어 제품 파손 위험, 공급 방향, 장비 간 속도 불일치, 제품 배열, 안전 요구조건, 설비 설치 공간 등이 해당할 수 있다.

단, 고객이 명시하지 않은 요구를 확정된 사양처럼 작성해서는 안 된다.

# Ⅷ. 여섯 번째 기능 — URS 내부의 요구사항 모순 탐지

## 1. 페이지 간 사양 대조

고객 URS는 같은 제품이나 장비를 서로 다른 페이지에서 설명할 수 있다.

프로그램은 문서 전체를 분석하여 동일 대상의 요구사항이 충돌하는지 찾아야 한다.

예를 들어 3페이지에 이너박스 길이가 165mm라고 기재되어 있고 8페이지에서는 160mm라고 기재되어 있다면 확인 대상이 된다.

## 2. 발견 대상

- 동일 제품의 치수 불일치
- 생산속도 또는 처리량 차이
- 서로 다른 제품 수량과 포장 배열
- 장비 구성에 대한 상충 요구
- 공정 순서 불일치
- 설치 조건 및 안전 요구의 충돌
- 앞뒤 페이지에서 서로 다른 단위 사용
- 제품 코드 또는 모델명 혼동

## 3. 단순 차이와 실제 모순의 구분

서로 다른 숫자가 나왔다고 무조건 오류인 것은 아니다.

예를 들어 외형 치수와 내측 치수의 차이, 서로 다른 제품 규격, 허용오차 등이 있을 수 있다.

따라서 AI는 대상 제품과 조건, 단위 및 문맥을 비교해 실제 충돌인지 판단해야 한다.

명확하지 않은 경우에는 **잠재적 모순 또는 고객 확인 필요**로 표시한다.

## 4. 원본 근거 연결

각 충돌 후보는 다음 정보를 제공해야 한다.

- 관련 제품과 설비
- 첫 번째 원본 위치와 값
- 두 번째 원본 위치와 값
- 차이가 발생한 이유
- 기술적으로 중요한 이유
- 고객 확인 필요 여부

직원이 충돌 후보를 클릭하면 원본의 관련 위치를 확인할 수 있어야 한다.

# Ⅸ. 일곱 번째 기능 — 고객 기술질의 자동 생성

기술 분석과 모순 탐지 결과를 바탕으로 고객에게 확인해야 하는 질문을 작성한다.

질문은 단순히 많이 만드는 것이 목적이 아니다.

**설비 검토와 견적·설계에 실제로 필요한 정보가 무엇인지 파악하는 것이 목적**이다.

질문 유형에는 다음과 같은 항목이 포함될 수 있다.

- 제품의 정확한 크기와 허용오차
- 제품 공급 방향 및 형태
- 제품별 공급 속도
- 1개 박스당 제품 수량
- 포장 배열 및 적층 방식
- 실제 생산품 샘플 제공 여부
- 기계 설치 공간 및 유틸리티 조건
- 상충하는 사양 중 최종 기준
- 요구 속도의 측정 단위와 조건

프로그램은 각 질문에 **왜 이 질문이 필요한지, 어떤 원문을 근거로 작성했는지** 표시해야 한다.

직원은 질문을 수정하거나 삭제할 수 있어야 한다.

필요하다면 고객에게 전달할 영문 질문으로 작성하는 기능도 활용할 수 있다.

단, 원문의 불명확한 부분을 AI가 임의로 해결한 뒤 확정된 사양처럼 표시해서는 안 된다.

# Ⅹ. 여덟 번째 기능 — 원문과 번역본 병렬 비교 시스템

이 기능은 최초부터 요구한 핵심 사용자 기능 중 하나이다.

**직원이 왼쪽에서 외국어 원본을 보고, 오른쪽에서 한국어 번역을 보면서 같은 내용을 직접 비교할 수 있어야 한다.**

## 1. 화면 구성

기본 화면은 다음과 같이 구성할 수 있다.

| 왼쪽 | 오른쪽 |
|---|---|
| 외국어 원본 PDF | 한국어 번역 내용 |
| 원본 페이지 | 대응하는 한국어 문장 |
| 원본 표와 그림 | 번역된 표·설명 |
| 원본 문장 강조 | AI 검증 결과 |
| 요구사항 위치 | 수정·검토 기능 |

직원이 원본과 번역 사이를 계속 오가면서 파일을 따로 열 필요가 없어야 한다.

## 2. 페이지 및 문장 연결

번역문에서 특정 요구사항을 선택하면 대응하는 원문으로 이동해야 한다.

원문과 번역문의 페이지가 정확히 일대일로 대응하지 않는 경우에도 **페이지 번호만 억지로 맞추는 것이 아니라 실제 대응하는 문장이나 표 셀을 기준으로 연결**해야 한다.

## 3. 마우스 하이라이트

이 기능은 특별히 요구했던 사항이다.

직원이 한국어 번역문 위에 마우스를 올리거나 클릭하면, 해당하는 원본 문장 또는 표 셀의 위치가 강조되어야 한다.

예를 들어 번역문의 "최소 생산속도 120팩/분"을 선택하면 왼쪽 원본 PDF의 "minimum speed of 120 packs/min" 위치가 표시되는 방식이다.

표 안의 값도 가능하면 원본 셀과 연결되어야 한다.

## 4. 검증 오류 표시

AI가 발견한 오류가 있는 문장은 직원이 쉽게 확인할 수 있어야 한다.

직원이 해당 항목을 선택하면 원문, 번역문, 오류 이유, 수정 결과, 재검증 상태를 확인할 수 있도록 한다.

## 5. 원문 그림과 표 비교

문장뿐 아니라 표, 사진, 공정도, 도면도 비교할 수 있어야 한다.

번역 과정에서 시각자료가 손실되거나 위치가 바뀌면 직원이 이를 확인하고 검토할 수 있도록 한다.

# Ⅺ. 아홉 번째 기능 — 직원의 AI 대화형 수정

프로그램 안에서 직원이 ChatGPT와 대화하면서 보고서를 수정할 수 있어야 한다.

예를 들어 직원은 다음과 같이 요청할 수 있다.

"이 카토너의 작동 원리를 초보자도 이해할 수 있도록 다시 설명해 줘."

"이 표에 있는 제품별 생산속도를 다시 비교해 줘."

"3페이지와 8페이지의 치수 차이를 분석해 줘."

"고객에게 확인해야 할 질문만 별도로 정리해 줘."

"이 번역문은 원문에 더 충실하게 수정해 줘."

프로그램은 해당 요청과 관련된 원문·번역·분석 결과를 참고해 수정안을 생성한다.

## 수정 후 반드시 해야 하는 작업

**AI 또는 직원이 변경한 내용에 대해서는 관련 검증을 다시 수행해야 한다.**

검증 완료된 숫자나 기술적 조건이 수정 과정에서 달라질 수 있기 때문이다.

특히 이미 승인된 내용을 수정한다면 기존 승인 결과를 그대로 유지해서는 안 된다.

수정 내용의 범위와 영향을 확인하고 필요한 부분을 재검증해야 한다.

# Ⅻ. 열 번째 기능 — 전문적인 한국어 문서 및 기술 보고서

프로그램은 최소한 두 가지 성격의 결과물을 지원해야 한다.

이것이 두 개의 별도 프로그램을 뜻하지는 않는다.

## A. 원본 충실 한국어 URS 번역본

목적은 고객이 작성한 원문을 한국어로 정확하게 전달하는 것이다.

핵심 요건은 다음과 같다.

- 원본 전체 문장 번역
- 원본 요구사항 순서 보존
- 원본 표·그림·사진·도면 보존
- 수치·단위·제품 코드 정확성
- 번역 누락 없음
- 한국어 문법과 전문 용어 일관성
- 원본 출처 추적
- Word/PDF 출력

이 문서에서는 고객의 요구사항과 AI가 추가한 설명을 혼합하지 않아야 한다.

## B. 한국어 URS 기술 분석 보고서

목적은 직원이 URS를 이해하고 실제 설비 검토에 활용하는 것이다.

보고서에는 다음 내용을 포함한다.

| 보고서 구성 | 주요 내용 |
|---|---|
| 프로젝트 개요 | 고객사, 공장, 프로젝트 목적 |
| 제품 정보 | 제품 종류·크기·포장 방식 |
| 공정 흐름 | 설비 및 공정 순서 |
| 설비별 사양 | 생산속도, 구조, 소재, 제어 등 |
| 기술 설명 | 설비 기능과 작동 원리 |
| 주요 요구사항 | 설계상 중요한 필수 조건 |
| 생산능력 분석 | 제품별 속도, 공정 간 연결 |
| 기술 검토사항 | 설비 구성과 잠재적인 문제 |
| 사양 모순 | 원문 간 불일치 및 확인 필요 사항 |
| 고객 기술질의 | 고객에게 확인할 질문 |
| 원본 시각자료 | 표·사진·도면·공정도 |
| 검증 및 승인 | 검증 결과, 검토 필요 사항, 승인 기록 |

## 1. 전문적인 문서 품질

보고서는 단순한 AI 응답을 복사한 형태여서는 안 된다.

제목과 문단 구조가 명확하고, 적절한 표와 강조 표시를 사용해야 한다.

한국어가 자연스럽고 전문적이어야 하며, 동일한 내용을 불필요하게 반복해서는 안 된다.

## 2. 클릭 가능한 개요표

보고서 첫 부분에서 각 장의 내용을 확인할 수 있어야 한다.

특정 항목을 클릭하면 해당 장으로 이동하도록 구성한다.

직원이 원하는 내용을 빠르게 찾을 수 있어야 한다.

## 3. Word/PDF 출력

보고서는 Word와 PDF 형식으로 출력할 수 있어야 한다.

최종 출력물은 실제 파일을 열어 다음 항목을 확인해야 한다.

- 본문 누락 여부
- 표와 그림 보존 상태
- 수치 및 제품 코드 정확성
- 글자 깨짐
- 문장 중복 및 문법 오류
- 표와 이미지의 레이아웃
- 클릭 개요표의 실제 작동
- 원문과 보고서 내용의 일치 여부

**Word/PDF 파일을 생성했다는 이유만으로 보고서가 완성된 것은 아니다.**

# XIII. 열한 번째 기능 — 직원 계정 및 작업 관리

## 1. 직원 로그인

프로그램은 비밀번호 기반 직원 로그인을 지원해야 한다.

직원은 승인된 접근 권한으로 프로젝트와 고객 문서를 확인한다.

## 2. 프로젝트 관리

업로드한 URS와 번역·분석 결과는 관련 프로젝트에 연결되어야 한다.

직원은 원본 문서와 번역 결과, 검증 기록, 기술 보고서를 같은 작업 안에서 확인할 수 있어야 한다.

## 3. 작업 상태 확인

프로그램은 현재 어느 단계까지 처리되었는지 보여줘야 한다.

직원은 번역과 검증이 실제로 완료된 것인지, 오류가 발견되었는지, 사람 검토가 필요한지 알 수 있어야 한다.

## 4. 수정 및 승인 기록

직원이 수정하고 검토한 내용, 검증 결과 및 최종 승인 이력을 남겨야 한다.

미승인 보고서와 승인된 최종 보고서를 구분해야 한다.

# XIV. 열두 번째 기능 — 단계별 엄격한 PASS 검증

## 1. PASS의 정확한 정의

**PASS는 해당 단계의 모든 필수 결과가 원문 또는 정해진 기대 결과와 정확히 일치하고, 필요한 검증이 완료된 상태만 의미한다.**

단순한 실행 성공, 파일 생성, API 호출 성공, 일부 문장 검사 성공, AI 자체 평가만으로 PASS가 될 수 없다.

번역 단계에서는 한국어 문자열이 원문과 문자 그대로 같아야 한다는 의미가 아니라 **기술적 요구조건과 의미가 원문에 충실해야 한다**는 뜻이다.

## 2. 반드시 구분해야 하는 상태

| 상태 | 의미 |
|---|---|
| PASS | 해당 단계 필수 검증 전부 통과 |
| FAIL | 실제 오류 발견 |
| NEEDS_REVIEW | 사람 검토가 필요한 미해결 사항 |
| UNVERIFIED | 필요한 검증 미실행 |
| BLOCKED | 필수 실행 조건 불충족 |
| NOT_IMPLEMENTED | 필요한 기능 미구현 |

FAIL, NEEDS_REVIEW, UNVERIFIED, BLOCKED, NOT_IMPLEMENTED 상태를 PASS로 취급해서는 안 된다.

## 3. 단계별 진행 차단

원본 보존 단계가 필수 검증을 통과하면 번역 단계로 이동한다.

번역 단계가 필수 검증을 통과하면 독립 의미 검증 단계로 이동한다.

독립 검증과 자동 수정·재검증을 통과하면 기술 분석 단계로 이동한다.

기술 분석과 필요한 검토가 끝나면 보고서 생성 및 검증으로 이동한다.

최종 보고서의 필수 검증과 직원 검토가 끝난 뒤 승인한다.

**앞 단계가 PASS하지 않았다면 다음 정식 단계로 넘어가지 않는다.**

단, 개발용 격리 시험은 실제 업무의 PASS나 정식 단계 완료로 기록하지 않아야 한다.

## 4. 정확도 목표

원래 요구한 핵심 품질 목표는 다음과 같다.

**문장 전체의 기술적 의미 정확도 99% 이상, 중대한 기술·안전 오역 0건.**

이는 달성해야 할 목표이지, AI를 연결했다고 자동으로 만족하는 수치가 아니다.

실제 원문 대조와 검증 근거 없이 정확도가 달성됐다고 표시해서는 안 된다.

## 5. 검증 근거와 신뢰도

직원은 단순한 AI 신뢰도 숫자가 아니라 다음 정보를 확인할 수 있어야 한다.

- 어떤 원문을 검증했는가
- 무엇과 비교했는가
- 어떤 검사에서 통과했는가
- 어떤 오류가 발견됐는가
- 수정이 완료됐는가
- 아직 사람이 검토해야 할 내용이 있는가

근거 없이 99% 또는 100% 신뢰도라는 숫자를 만들어서는 안 된다.

# XVII. 실제 개발 방향과 구현 원칙

## 1. 기존 프로그램을 보존한다

이미 개발한 기능을 무조건 삭제하거나 전면 재개발하지 않는다.

기존 로그인, PDF 업로드·추출, 표·그림 보존, 병렬 비교, 수치 검사, 기술 분석, 단계 게이트, Word/PDF 생성 기능을 계속 활용한다.

미완성인 기능은 원래 요구사항에 맞게 완성한다.

## 2. ChatGPT의 능력을 직접 활용한다

ChatGPT/OpenAI가 이미 제공하는 문서 이해, 번역, 의미 검증, 오류 수정, 기술 분석, 보고서 작성 능력을 활용한다.

같은 기능을 수행하는 자체 AI 모델이나 독립적인 AI 연구 플랫폼을 새로 만들지 않는다.

## 3. 기존 프로그램과 OpenAI의 역할을 연결한다

OpenAI는 번역·의미 해석·오류 수정·기술 설명을 수행한다.

기존 프로그램은 원본 자료 보존, 결과 연결, 검증 기록, UI, 직원 검토, 문서 출력, 승인 등을 관리한다.

단, 이는 **기존 기능을 없애거나 담당 범위를 임의로 축소하라는 뜻이 아니다.**

기존 PDF 추출·수치 검증·기술 분석 기능은 필요한 곳에서 계속 함께 활용한다.

## 4. 불필요한 중복 개발을 피한다

구현 전에 다음을 먼저 확인한다.

- OpenAI가 이미 제공하는 기능인가?
- 기존 프로그램에 같은 기능이 있는가?
- 기존 PDF 라이브러리로 처리할 수 있는가?
- 원래 33개와 추가 5개를 충족하는 데 꼭 필요한가?
- 현재 작업이 실제 결과물의 품질 향상에 기여하는가?

새로운 개발이 꼭 필요하지 않다면 기존 기능을 활용한다.

## 5. 하나의 프로그램에서 처리한다

새로운 로그인 시스템, 번역 프로그램, 보고서 프로그램, 검증 연구 플랫폼 등을 따로 만들지 않는다.

직원은 하나의 통합 프로그램에서 필요한 작업을 수행해야 한다.

## 6. 보안과 비용을 관리한다

회사에서 승인한 OpenAI API를 사용한다.

API 키는 서버에서 안전하게 관리하고 화면·소스코드·로그에 노출하지 않는다.

고객자료 전송은 회사 및 고객의 해당 자료 처리 권한을 준수한다.

API 사용량과 비용을 제한하고 자동충전은 금지한다.

실제 번역·검증 결과가 필요하지 않은 불필요한 API 재호출을 줄인다.

## 7. 개발 순서와 PASS 기준을 준수한다

해당 단계의 필수 기능과 검증을 완료한 후 다음 정식 단계로 진행한다.

기존 기능을 보존하면서 오류가 확인된 부분만 수정한다.

합성 시험 PASS를 실제 모든 고객 URS 문서의 검증 완료로 확대해서는 안 된다.

반대로 모든 가능한 PDF 형식을 무한정 시험하기 위해 필수 프로그램 개발을 지연시켜서도 안 된다.

**최초 요구사항에 맞는 명확한 검증 범위를 정하고, 그 범위를 완전히 통과한 뒤 단계적으로 완성한다.**

# XVIII. 최종적으로 직원이 받아야 하는 결과

프로그램이 완성되었을 때 직원은 다음과 같은 업무를 수행할 수 있어야 한다.

**상황: 해외 고객으로부터 12페이지짜리 영어 URS를 받았다.**

직원은 프로그램에 로그인하고 PDF를 업로드한다.

프로그램은 원본 내용을 보존한 채 ChatGPT를 통해 한국어 번역을 수행한다.

번역된 모든 요구사항을 원본과 독립적으로 검증하고, 잘못 번역된 내용을 AI가 수정한 뒤 다시 검증한다.

검증 중 발견된 불확실한 사항은 직원 확인 대상으로 표시한다.

이후 프로그램은 해당 고객의 제품 종류, 공정 순서, 생산속도, 설비별 요구사항을 분석한다.

서로 다른 페이지에 상충하는 치수가 있다면 그 원문 위치와 함께 표시한다.

고객에게 확인해야 할 기술 질문을 작성한다.

직원은 왼쪽 원본 PDF와 오른쪽 한국어 번역문을 나란히 보면서 원문 위치를 하이라이트하고, 필요한 부분을 확인한다.

기술 설명이 어렵다면 AI에게 쉽게 다시 작성해 달라고 요청할 수 있다.

수정된 보고서는 필요한 검증을 다시 수행한다.

검증이 완료되고 직원 승인이 끝나면 전문 한국어 URS 번역본과 기술 분석 보고서를 Word/PDF로 출력한다.

**이것이 처음부터 요구했던 URS AI REPORT SYSTEM의 완성된 업무 모습이다.**

**URS AI REPORT SYSTEM은 해외 고객 URS의 외국어 원문을 보존하면서 ChatGPT/OpenAI로 정확하게 한국어 번역하고, 독립적인 기술 의미 검증과 자동 오류 수정·재검증을 수행하며, 설비 기술 분석·사양 충돌 탐지·고객 질의 작성·전문 보고서 생성을 지원하고, 직원이 원문과 번역을 직접 비교·수정·승인할 수 있는 하나의 사내 통합 업무 프로그램이다.**

이 정의와 최초 33개 및 초기 추가 5개 요구사항이 앞으로의 모든 개발·수정·검증 작업의 판단 기준이다.
