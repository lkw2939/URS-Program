# 분석 보고서 필수 구성

요구사항 정의서 XII-B의 12개 구성을 출력 단계에서 보장한다.

| 순서 | 구성 | 정보 출처 |
|---|---|---|
| 1 | 프로젝트 개요 | 원문에 있는 고객사·공장·목적 |
| 2 | 제품 정보 | 원문 제품·크기·포장 정보 |
| 3 | 공정 흐름 | 원문 공정과 연결·순서, 불확실한 순서는 확인 필요 |
| 4 | 설비별 사양 | 원문 설비·속도·구조·제어 등 |
| 5 | 기술 설명 | 원문을 근거로 한 AI 해설, 고객 요구와 구분 |
| 6 | 주요 요구사항 | 설계·안전 필수 조건 |
| 7 | 생산능력 분석 | 처리 단위·포장비·조건, 불명확한 환산 금지 |
| 8 | 기술 검토사항 | 원문 근거가 있는 위험·확인사항 |
| 9 | 사양 모순 | 양측 출처 및 잠재/확정 구분 |
| 10 | 고객 기술질의 | 한영 질문·이유·출처 |
| 11 | 원본 시각자료 및 출처 | 해시 검사한 전체 페이지 |
| 12 | 검증 및 승인 | 생성 시점 리비전·원본 해시·단계별 상태·미승인 표시 |

분석 항목에 topic과 coverage를 요구한다. supported는 유효한 원문 출처를 필수로 갖는다. 전체 분류가 원문에 없으면 not_stated, 빈 source_ids, 고정 문구 ‘원문에 명시되지 않음 — 고객 확인 필요.’만 허용한다. 실제로 원문에 없는지는 독립 분석 검증 및 직원 원문 대조가 판단한다. 분류가 존재한다는 사실만으로 내용의 정확성을 인증하지 않는다.

필수 분류가 빠지거나 잘못된 분류·상태·출처가 있으면 분석을 실패 처리하고 출력 단계로 넘어가지 않는다. 출력에서도 필수 구성을 다시 검사한다. Word/PDF를 재열어 제목·본문을 확인하고, LibreOffice로 변환한 PDF에서도 12개 제목과 미승인 표시를 확인한다.

파일은 직원 승인 전에 만들어진다. 따라서 ‘생성 시점 미승인’을 정확히 표시하며 이후 승인 여부를 고정 파일 내용으로 추정하지 않는다. 최신 승인/수정/재검증 이력은 별도 문서별 검증 기록 HTML/JSON에서 확인한다. 최신 구현은 승인 시 검토한 본문을 보존하고 뒤에 직원 최종 승인 기록을 추가한다. 승인자·KST 시각·검토 근거·원본/검토 본문 해시를 포함한다. 승인과 최종 파일4개/해시를 같은 DB 트랜잭션으로 저장하며 동시 수정·검증 변경·생성 실패 시 승인하지 않는다. 최종 다운로드는 현재 승인·평가 자격·코드/모델 및 최종 파일 해시를 다시 확인한다.

기존 스키마의 분석 결과는 필수 분류 없이 새 출력 검사를 통과하지 못한다. 분석을 다시 실행하거나 올바른 전체 분석 수정안을 제출한 뒤 독립 검증이 필요하다. 현재 실제 API는 보류 중이므로 실제 고객 결과를 강제로 재생성하거나 승인하지 않는다.
